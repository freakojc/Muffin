# 1 GiB Markdown 打开耗时与下一步优化

日期：2026-10-18。当前每次解析独立分配器和公开 API 同步封装已进入测量产物；本轮只修改说明文档并运行隔离探针，没有修改产品算法或第三方源码。

## 当前版本的阶段复测

使用现有 `build/stress-1g-20261017/muffin-mixed-1gib.md`：1,073,741,824 字节，912,891,904 个 UTF-16 单位，中英文混合，包含标题、列表、表格、代码与数学，无外部图片。SHA-256：`6a4fd4c4f47be52d284008adc87586a5f6df90277e62bd37d2b36d677b7ef16a`。

独立 Release `/O2` Core 探针加载当前 `build/Release/MuffinCore.dll`，每轮新进程、先解析一个很小的预热文本，再解析完整文件。记录粗阶段，不开启逐节点计时。三轮顺序运行，文件缓存温热；不是冷盘或前台 GUI 首屏验收。

| 阶段 | 三轮中位数 | 样本范围 | 说明 |
| --- | ---: | ---: | --- |
| 探针读取、UTF-8 解码、释放字节缓冲 | 1.074 s | 0.942–1.089 s | 未包含产品的编码识别、格式处理和打开对话框 |
| 完整 Markdown 解析 | **23.682 s** | 23.388–23.693 s | 包含下表全部解析子阶段 |
| 再次检查共享文本绑定 | 0.647 s | 0.641–0.680 s | 按现有 session 准备顺序调用 |
| 后代相对坐标准备 | 0.778 s | 0.772–0.882 s | 保持现有块坐标模型 |
| 未完成 Markdown 标记收集 | **19.410 s** | **18.484–23.736 s** | 返回偏移数为 **0**，仍对大量普通段落完整识别 |
| PieceTable 文本索引准备 | **6.843 s** | 6.798–6.866 s | 换行位置、词起始位置及汇总 |

解析内部的主要阶段：

| 子阶段 | 三轮中位数 |
| --- | ---: |
| cmark feed/finish | 5.641 s |
| 转换为 Muffin AST，含消费后的 cmark 子树释放 | **10.301 s** |
| 行起点及 ASCII 标记准备 | 1.347 s |
| UTF-8 输入缓冲准备 | 0.610 s |
| 定义扫描 | 0.422 s |
| 顶层虚拟空段落整理 | 0.965 s |
| 删除线处理 | 1.005 s |
| 表格单元格范围标注 | 0.644 s |

各阶段独立取中位数，不能直接相加得到中位总时间。解析还包含其他范围标注、容器处理、分隔符探测和缓冲释放，完整明细见 [JSON](large-document-open-analysis-2026-10-18.json)。标记收集和文本索引在解析结束后计时，不在 23.682 秒内。

三轮节点统计一致：**6,130,690** 个块、**7,088,129** 个行内节点，其中 **5,746,688** 个直接共享原文；无解析诊断。首轮完整 AST、文本、源码坐标与共享状态指纹与分配器接入前的参考一致。指纹和节点遍历不计入上述阶段，但会影响后续缓存状态；保留第一轮较慢的标记收集样本。

采样峰值私有提交约 **11.89 GiB**，不是文件大小或最终 AST 的内存。每个探针受 Windows Job 的 14 GiB 上限、13 GiB 软停止及可用提交检查约束；没有触发停止条件。原始内存采样不等同于逐项堆归因。

## 优先级一：收紧未完成标记的候选范围

入口位于 `src/document/PendingBlockMarker.cpp` 的 `collectPendingMarkerOffsets()`。目前每个 Paragraph 都进入 `pendingMarkerStartInLine()`，尝试标题、列表、代码围栏和数学标记，并可能剥离容器前缀重试；普通段落也支付换行检查、正则匹配等开销。

隔离原型仅在收集入口增加保守筛选：跳过前导 Unicode 空白，首字符不是 `# - + * \x60 ~ $ \\ >` 或 Unicode 数字时，跳过完整识别。候选继续调用原识别逻辑，不改渲染、Enter 提交和标记语义。

同一个完整 1 GiB 解析树上的探索对照：

| 收集方式 | 耗时 |
| --- | ---: |
| 产品原收集器，一次 | **21,524.70 ms** |
| 入口筛选原型，三次 | **262.48 / 250.69 / 273.18 ms** |

完整偏移数组一致，均为空。此样例对筛选有利；这是一个树上的三次收集，不是三个独立打开进程，不外推所有文档的收益或 p95/p99。此前 `build/pending-marker-study/` 的研究已核对 **232,640** 组字符串，覆盖 Unicode 空白/数字、容器、有效标记和局部坐标；候选密集时收益很小，因此仍需保留该边界。

这是下一轮最值得正式接入的变更：范围小、已有完整样例证据、全部位于 Muffin 层，也不改变估高、总高度或滚动锚点。接入后仍须验证有效标记、输入提交、撤销、同步/异步解析和局部编辑，并重测真实 GUI 打开与连续滚动。

## 优先级二：减少初始布局准备中的重复计算

此前实际 GUI 基线打开到 Qt 首帧为 **83.30 秒**，同步发布及视图准备约 **21.63 秒**；另一轮详细记录中，约 211 万个顶层块的骨架循环约 **16.99 秒**。这些是 2026-10-17 的旧版本测量，不能把本轮解析或原型的改善直接从 83.30 秒中扣除。

`DocumentLayout.cpp` 的 `layout.skeleton` 会逐块计算间距和估高，再建立位置与嵌套索引。正文估高已有样式/宽度缓存，应继续检查重复的间距解析、列表字体度量、盒模型复制与容器遍历，而非再次增加同类缓存。

可研究在一次布局期间复用相同类型、标题级别、宽度、主题与字体代次下的不可变结果，并将块结果计算与文档顺序前缀累加分开计时。必须保持原有高度公式、边距折叠与索引语义，先用新 GUI 阶段数据确认热点。暂不重新引入后台补估高、粗化高度或边滚动边修正整篇高度的方案。

## 优先级三：文本索引构建与有预算的并行准备

`PieceTable.cpp` 的构造函数逐字符调用 `isLetterOrNumber()` 并记录换行和词起点。样例包含 **7,282,689** 行和 **124,482,560** 个词；大量词起点记录还增加分配和写内存成本。

先测 ASCII 快速判断并对非 ASCII 保留现有 Unicode 规则，核对数字、下划线、中英文、组合字符及 UTF-16 边界；再检查容量增长和重复扫描。不要通过跳过字数或换行索引来提速。

文本索引依赖不可变原文，可以研究与 Markdown 解析在后台并行，最多重叠当前约 6.84 秒的独立工作，但实际收益受内存带宽和调度影响。应限制并发和临时内存：当前解析峰值已接近 12 GiB，并行建立大量词索引可能抬高峰值；取消打开、过期结果和对象生命周期也必须正确处理。

## 后续：AST 转换与后处理

AST 转换仍约 10.30 秒，需在当前分配器版本重新细分行内范围标注、解码/共享资格检查、容器增长和回收。旧诊断中的块对象裸分配只有约 0.46 秒，不能把整个转换阶段都归因于 `new`；先前容量预留和坐标缓存实验也不支持把它们当作主要提速方向。

可按节点类型或语法候选减少后处理中的全树访问，但删除线已经有全文/行内候选检查，不能将其作为尚未实现的优化。顶层虚拟段落、表格范围和容器整理有依赖顺序，合并遍历前必须逐项核对。

并行 AST 转换的风险较高：当前适配器递归修改并释放 cmark 链接，分配器也不能由多个线程同时操作；还涉及脚注跨定义引用、坐标缓存、顺序和额外存活内存。不直接并行现有循环，也不为此新增第三方内部接口。单纯把更多工作移到后台只能改变界面阻塞，不能自动缩短打开总时间。
