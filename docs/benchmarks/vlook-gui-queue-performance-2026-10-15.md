# 原生 GUI 排队时间线与不透明视口绘制

本轮关联输入计划/投递、Qt 派发、实际脏区请求、窗口更新、首次视口绘制和 Windows GUI 线程观测。修复了光标刷新时反复绘制编辑器下方父容器的问题，并开始复用首次可见排版中的最终样式指纹。原始操作与异常窗口见[诊断 JSON](vlook-gui-queue-diagnostic-2026-10-15.json)。

## 测量与证据边界

沿用固定 VLOOK Fancy Dark、Qt 6.11.1、Noto Serif、96 DPI、DPR 1、1100×820 窗口。单页视口 1086×761，屏幕报告刷新率 32 Hz。CSS SHA-256 为 `dc9ce7c464f4ddf8644040fb77c7c7e408a70f1bee3ba2c9f9a8ac746901f3cc`。每组使用新进程，正常后台草稿，详细 trace 开启；GUI 测量期间没有并发构建或测试。

独立生产者按固定节奏投递 Qt 操作事件，键盘阶段各 80 次、间隔 50ms；同时保留冷/热滚动及 12 次主题动作。这里的派发不是 Windows 实体键盘输入，绘制完成指 QWidget paint 返回，不代表 DWM 呈现。原口径保留没有改变光标的按键和合并绘制，并分别标记实际变化，不能把无操作按键等到后续绘制的时间都视作编辑停顿。

默认关闭的 `muffin.perf.queue` 在真实 `QWidget::update` 请求处记录脏区，保持 Qt 异步合并语义。详细 trace 关联生产者 due/post、Qt handler、dirty request、UpdateRequest/UpdateLater/Paint、定时器、dispatcher awake/aboutToBlock 与 native message；带进程/线程 id 和 QPC/steady clock 元数据的新记录可用于后续系统跟踪。嵌套 Qt handler 的覆盖时间取区间并集，不能累加父子事件。

Windows CPU 记账精度较粗，cycle 不能按固定频率换算成毫秒。额外六份 `scheduler_diagnostics` 用后台 `NtQuerySystemInformation` 点采样 GUI 线程状态；系统查询会增加诊断开销，不能与修改前仅含 CPU/cycles 的记录混作性能对照。最终 `after` 六份恢复与修改前相同的 CPU/cycle 采样。20ms 点采样不提供精确 ready 时间或阻塞调用栈，WaitReason 仅在 Waiting 状态有意义。dispatcher 的两个信号也不能直接视为实际睡眠的起止。

首批线程状态记录在系统查询前读取 CPU、查询后打时间戳，存在采样区间偏移；不能将其 CPU 差值视为准确的时间点观测。后续基准记录整个查询区间并在查询后读取 CPU。状态诊断中的 1 MiB 上下移动 p95 曾达 **162ms**、最大 **272ms**，其中一次 paint 约 **70ms**，CPU 也增长明显；不将它全部归为等待，也不将它简单归因于查询成本。该样本同样保留。

尝试开启 WPR CPU recording 时，本机策略返回 `0xc5585011`；没有修改策略，也没有取得 ETW 调度栈。因此本轮保留系统调度/等待的未决部分，不能断言已消除所有偶发长尾。工作集同样每 20ms 采样，不代表堆大小或保证峰值。

## 复现的 10 MiB 左右移动长尾

修改前两轮分别测量 1/10/30 MiB 单页。第一轮 10 MiB 左右移动绘制 p95 为 **152ms**，有 **10 次实际变化的输入等待达到 100ms**；第二轮相同配置 p95 为 **18.7ms**，说明存在明显波动。两轮 1 MiB 输入和 30 MiB 上下移动未复现此前的大长尾。

最长一次左右移动约 **203.35ms**，原始样本 index 47 的时间线如下，单位为该阶段开始后的毫秒：

| 点 | 时间 |
| --- | ---: |
| 计划投递 | 2380.28 |
| 实际投递 | 2382.13 |
| Qt 操作开始 | 2439.81 |
| 操作处理结束 | 2456.54 |
| 视口开始绘制 | 2581.74 |
| 视口绘制结束 | 2583.64 |

同步处理约 **16.73ms**，实际投递到派发约 **57.68ms**，处理结束到绘制开始约 **125.2ms**，绘制本身约 **1.9ms**。随后若干操作共享这次绘制。等待区间有其他输入和嵌套 Qt 事件，不能把整段未覆盖时间直接归为系统调度；但 CPU/cycles 增量较少，也没有一个同样长的排版回调解释这次停顿。

该阶段 `view.prefetch` 最大 **0.0614ms**，其中构建最大 **0.0107ms**、trim 最大 **0.0022ms**。这一样本不支持把百毫秒等待归因于预取/回收；冷滚动进入新区间时仍有独立构建成本。

## 确认并修复的重复父背景绘制

EditorView 已经在所有文档、空页和加载分支之前完整填充每个 dirty rect，但 Qt 此前仍为视口刷新绘制底下的分隔器、堆叠容器等祖先背景。对实际背景 alpha=255 的视口设置 `WA_OpaquePaintEvent`，并在主题、字体、缩放和响应式环境更新时同步。半透明背景恢复父背景合成。

修改前，10 MiB 左右移动阶段视口 70 次绘制同时带来 QSplitter、两层 QStackedWidget 和中间 QWidget 各 70 次绘制。第一份有效修改后记录中，左右移动阶段这些容器的绘制次数均为零；主窗口仍因状态栏更新收到 paint，不等于整个父窗口完全停止绘制。新增回归验证光标小脏区不绘制父背景、完整背景颜色正确，以及媒体查询在不透明/半透明之间切换。

## 首次可见排版中的样式指纹复用

最终计算样式在多个行内片段和交互状态之间共享，而其指纹仍重复遍历属性、长度和 grid 轨道。新增最多 128 项的线程本地内存 memo，以精确标量和 Qt 共享存储身份验证命中；保留不可变值快照，让正常 map 修改通过 detach 失效。图片资源 owner 和 AST 不进入 memo，原指纹值及后续完整值比较保持一致。

回归覆盖属性/变量/长度、嵌套 grid 轨道、字体/缩放/视口、动画修改与淘汰。1/10/30 MiB 的独立 offscreen 样例全部与全量计数器结果一致，完整阶段记录见[排版 JSON](vlook-inline-first-layout-2026-10-15.json)。该组每种配置前后各一次，不能作为 GUI 延迟分布或稳定改善比例。

| MiB | 首次视口排版 wall：前 → 后 | 其中 CSS 独占：前 → 后 |
| --- | ---: | ---: |
| 1 | 106.2 → 72.9ms | 53.7 → 36.1ms |
| 10 | 76.5 → 71.3ms | 36.4 → 34.8ms |
| 30 | 94.1 → 86.2ms | 47.3 → 44.1ms |

冷缓存和系统噪声仍影响这些数值；首次绘制还包含字形/效果资源准备，30 MiB 首次 paint 约 104.8 → 103.7ms，没有明显改善。后续应使用真实 GUI 重复数据决定是否继续缓存行内样式/交互配方，而不是把单次排版变化外推为主题切换总收益。

## 相同 CPU/cycle 采样的两轮复测

最终两轮按相同节奏重放三类输入，省略后续滚动/主题阶段，避免拉长前台占用。三类输入的前置路径、80 次操作和间隔与修改前一致；六份记录均通过全程激活变化检查与暴露采样，无 trace 截断，隐藏视口 paint 为零。两轮 p95 如下，单位 ms：

| MiB | 输入同步 | 输入计划到绘制 | 左右同步 / 绘制 | 上下同步 / 绘制 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 36.8 / 16.3 | **269.6 / 35.8** | 2.2/15.5；2.2/12.5 | 14.1/68.6；12.0/68.9 |
| 10 | 18.7 / 19.0 | 34.9 / 40.0 | 2.0/12.0；3.9/12.3 | 13.7/69.4；12.7/69.0 |
| 30 | 24.1 / 22.7 | 46.4 / 38.8 | 3.2/16.6；3.6/15.4 | 13.5/68.1；13.3/70.3 |

10 MiB 左右移动未重现修改前第一轮 152ms p95；30 MiB 上下移动也未重现此前长尾。但 1 MiB 第一轮输入仍有 **17 次实际变化的操作超过 100ms**，最大 **369.62ms**；不能宣称偶发排队已修复。最长样本 index 28：计划 1430.23、投递 1431.95、派发 1559.54、处理结束 1595.32、开始绘制 1793.81、绘制结束 1799.85ms。单次同步 **35.78ms**、投递等待约 **127.59ms**、处理后等待约 **198.49ms**、绘制约 **6.04ms**。期间处理多个后续输入和状态刷新，CPU/cycles 持续增长；不是一次持续 370ms 的 paint 或 parse 调用。

Qt 合成操作事件可能积压并共享后续 paint；本基准未经过真实 Windows 键盘消息，不能据此调整产品事件优先级或强制同步 repaint 来“修复”测量结果。父背景绘制的重复工作已消除，持续输入下的累计处理/排队及偶发 paint CPU 峰值仍待独立定位。上下移动原口径约 68–70ms 包含无变化按键；每组 74 次实际移动的子集 p95 为 **28–35ms**，原始样本没有删除。

上下移动结束工作集按 1/10/30 MiB，两轮分别 **350.4/355.9、661.1/661.8、1424.5/1334.3MiB**，修改前为 **352.9/355.1、662.4/666.3、1336.9/1336.2MiB**。30 MiB 第一轮较高，同时该检查点后台草稿确认仍为 **0/82**，第二轮为 **82/82**；不能把该差值解释为缓存节省或判定泄漏，也不能声称六组此时都已确认持久化。此轮只读 checkpoint，短测量没有等待后台任务完全排空。

## 验收与未完成边界

另外尝试关闭详细 trace 的完整六组矩阵，但前两份在测量期间/结束时失焦；整份排除，不单独采纳其中看似正常的早期阶段。随后停止自己启动的测量进程/启动器，第三份无完整 JSON。两份完整原始记录及第三份中断日志保存在[排除记录](vlook-gui-queue-excluded-matrix-2026-10-15.json)。此前两份 10 MiB 详细 trace 的失焦记录也保留在诊断 JSON 的 `invalid` 中。

因此本轮完成三类输入的重复原生 GUI 对照，但**没有取得主题切换/多标签页的完整六组有效 GUI 验收**；需要在前台条件稳定时补测。offscreen 指纹收益不能替代这项验收。诊断汇总区分 `before`、相同采样 `after`、仅 opacity 的中间记录、线程状态诊断与失效记录，保留全部输入及每个异常窗口。
