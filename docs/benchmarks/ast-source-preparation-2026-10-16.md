# AST 转换、原文共享与 Unicode 坐标准备

本轮接续分隔符优化，拆分行内节点构造、UTF-8 解码、范围标注/裁剪、cmark 子树释放及后续共享绑定。详细诊断使用 `MUFFIN_AST_PROFILE=1`，逐节点时钟会扰动总时间，只用于定位；正式解析和 GUI 数据关闭这组诊断。

## 确认的热点与实现

30 MiB 详细 GUI 基线约 **382 万个 cmark 行内节点**：UTF-8 解码 **276ms**，范围标注 **451ms**（含坐标换算 **105ms**），相邻范围裁剪 **128ms**，cmark 子树释放 **148ms**；后续共享绑定 **378ms**。叶节点构造包含解码，递归 `inlineChildren` 计时会重叠，不能把所有项目相加。cmark 释放散布于转换期间，`parse.release_cmark` 仅覆盖剩余根节点和 parser，并非全部释放成本。

第一版交错 Core 样本又确认：1 MiB、每段十二次重复的中文/emoji 长行，AST 转换约 **584ms**，ASCII 同尺寸约 **46ms**。已有 ASCII 列换算是常数时间；非 ASCII 每次仍从行首重新扫描，成为新的主要热点。

- `parseDocumentShared()` 接受不可变原文所有者。适配器仅在 cmark literal 与对应原文片段精确相等时，直接创建 Text/HtmlInline 共享切片，避免先分配解码 QString 再释放。
- 无法精确共享的实体、转义、代码归一化、Unicode 重映射等继续解码。未匹配 backtick 的旧范围修正仍在回退路径执行。前置信息剥离后，语法范围仍相对解析窗口，切片引用使用原文绝对偏移。
- 分隔符片段保留原切片所有者及偏移；普通文本拆分后仍共享原文。最终 AST 继续执行完整绑定资格检查，同一原文、完全匹配 content 范围的已绑定节点快速返回。异常范围被裁剪时先解除直接绑定，按旧规则重新判断。
- 相邻范围裁剪只有实际变化时才重写范围；链接与图片标签拼接使用 `textView()`，减少共享文本转回临时 QString。
- 当前适配器只缓存最近一行的坐标检查点：约每 64 个 UTF-16 单位一个，非 ASCII 查询先二分定位，再扫描短段。正确处理 UTF-8 字节序列内部、surrogate pair、行尾截断及非顺序访问。缓存由当前解析器独占，解析结束即释放，不修改文档共享索引的线程安全约束，也不增加跨文档缓存。
- 原有适配器和列换算诊断的可变计数改为线程局部，避免多个解析 worker 互相覆盖。节点尺寸、语法信息、编辑坐标域和隐藏页更新策略不变。

## 正确性验证

保留前轮旧版分隔符 AST 指纹，4,368 次组合同时对比拥有字符串和直接切片解析的完整 AST、源码范围及序列化。新增共享切片生命周期、失败比较不改文本、实体/转义/代码归一化、YAML 前置信息、数学转换、Unicode 重映射、CR/LF、空文本、未配对标记及无效 UTF-16 对照；最终绑定资格也逐节点一致。

新增 **3,000 次**坐标查询独立 oracle，直接用现有逐字符扫描器比较随机行、非顺序列、多字节内部及跨检查点 surrogate pair，不复用解析器自己的结果作为预期。

Core 阶段 probe 在计时结束后对整个 AST 及绑定状态生成 SHA-256，与同一 EXE 加载旧版 Core 的结果比较。GUI 继续核对三主题的全量计数器、像素、字体、几何和光标命中，以及切页后输入、草稿排空和关闭对象释放。

## 测量方法

正式 Core 基准使用同一 `MuffinAstPerformanceProbe.exe`、旧新 DLL、新进程交错三轮，奇数轮先旧后新，偶数轮反序。三种尺寸 ASCII，加 1 MiB Unicode 和实体/转义样例；生成文档、构造 session、全量指纹及销毁均在 `wall_ms` 之外。同步 session 时长包含实际绑定和文本/节点索引准备，不等于 GUI 打开时长；GUI 仍使用实际异步路径。详细样本单独保留，不混入正式中位数。

六组 GUI **1/10/30 MiB × 单页/三页**，修改前每格一份，修改后每格两份，各另关闭诊断对照及启动样例。真实 Windows 前台、Qt 激活和可见检查；不与构建/CTest 同时运行。首次完整视口 QWidget Paint 不代表 DWM 呈现或原生键盘延迟。新生成文件立即打开，OS 文件缓存温热，非冷盘测量。前后 GUI 顺序测量，未交错；每格的小样本不能估计总体长尾。

另 **8 份**最终详细交错样本位于 `build/ast-final-details/summary.json`。30 MiB UTF-8 解码调用 **347.94 万→103.52 万**，其中 **244.42 万**个 literal 直接引用原文，覆盖约 **1929 万**个 UTF-16 单位。解码计时约 **282→63ms**、范围标注 **451→246ms**、裁剪 **129→83ms**；直接切片路径另约 **393ms**，叶节点构造包含该路径，不能重复相加或把解码下降全部当作净节省。此组 cmark 释放 **148→168ms**，没有改善释放机制。

首版共享切片、尚未加入坐标缓存的 30 份交错探索记录为 `build/ast-interleaved/summary.json`，最终正式数据单独保存，不混入。初始详细 GUI 定位在 `build/ast-before-profile.json`、`build/ast-after-profile.json`，它们含细粒度时钟扰动，不能当作正常首屏验收。

## GUI 补测结果

修改后 **12/12 正式进程、2/2 关闭诊断对照**及一份启动样例全部通过实际前台、激活、可见、整视口绘制和草稿检查，原始数据在 `build/ast-gui-gated`。每个正式进程四轮三主题，共 **144 次主题操作**。协调器只在全部进程退出后做统计、资源摘要及图像分析。

补测过程中确认工具原先只在输入阶段等待前台，用户稍晚点击时，文档已在后台打开。因此在手动 probe 的**每次打开之前**增加前台、Qt 激活、可见和编辑区焦点连续稳定 500ms 的门槛，随后才生成文件、开始打开计时。等待另存为 `open_foreground_wait_ms`，不算入首屏时间；超时停止链条，首屏和各阶段的实际前台验证仍保留。应用代码、DLL 和测试版本未改动。前后 probe EXE 摘要分别保留，不能称 GUI 使用了同一 probe 二进制；Core 交错实验仍使用同一 EXE。

### 内存与独立审计

30 MiB 单页打开采样峰值约 **1239.44→1239.01–1239.80 MiB**，基本不变；三页整体打开峰值 **2775.14→约2734 MiB**，约下降 **41 MiB**。三页草稿排空工作集 **2637.78→2596.21–2597.67 MiB**，原页关闭 5 秒后 **362.65→352.48–354.49 MiB**。AST 节点数、最终共享资格、字符串 payload 和布局容量一致，不能把工作集变化称为 AST 常驻容量再次压缩。20ms 工作集采样可能遗漏短峰值；全局 cmark 峰值未随转换结束读数同幅下降。

独立解码 **168 张 PNG**、复算 **2790 项统计、4500 个时钟差和 54 条打开时间线**，验证旧新 DLL/主题/字体摘要、后台解析线程、前台门槛、隐藏页与关闭状态。完整记录及审计见 [JSON](ast-source-preparation-2026-10-16.json)。阶段性能与功能验收已补齐，唯一静态背景纹理异常继续保留；本轮不进入 cmark 改造，下一轮先独立复现该视觉残留，再拆分 cmark 块解析、行内解析和扩展成本。
